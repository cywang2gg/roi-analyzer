# 色卡 24 Patch 定位＋數據擷取 — 架構書精簡版（v1.1 壓縮）

> 完整版：`docs/cc_patch_locate_architecture.md`（v1.1）。本版為壓縮版本，供快速閱讀與審查；兩者衝突時以完整版為準。
> 專案：`C:\Github\roi-analyzer`（純 C＋Win32＋GDI＋WIC，ANSI 全 A 版，`-Wall -Wextra` 零警告，C11）。基準為 `master` 分支。
> 來源：Python 原版 `ColorImageComparator_v8-2_d65.py`（working logic，以原版為準）；移植書 `偵測定位架構移植書.md`。
> 狀態：草案，待使用者審查後才發包開發。

## 一、目標與範圍

v3.3 已完成 YOLO 色卡框偵測（洋紅框＋狀態列）。本版往下一層：對偵測框內的色卡，定位出二十四個 patch 的矩形，在影像上疊加顯示，並擷取每格數據。

需求四項：偵測成功後對最高分 `color-chart` 框跑定位（裁切、網格線、取格），不阻塞介面，沿用常駐工作執行緒；成功時疊加二十四個 patch 矩形，與洋紅偵測框區隔，以列優先編號一至二十四；每格輸出 BGR 平均值、Y 平均值與標準差、Lab 平均值（sRGB 與 D65 白點），供後續色差與報表使用；任一步失敗回退手動四角點模式，不當機、不污染既有 ROI 與匯出。

範圍含定位、疊加顯示、數據擷取、設定、狀態列提示。不在範圍者為色差計算、報表與 CSV 匯出 patch 數據、依 patch 自動建立 ROI、GPU 加速。

## 二、前提與限制

L1：專案為純 C 與 MinGW 建置，第三方僅 OpenCV（動態連結）與 ONNX Runtime（動態載入）。L2：全程式使用 ANSI A 版介面，新增字串沿用既有中文介面做法。L3：維持零警告標準，新檔宣告置於區塊開頭，不使用雙斜線註解。L4：主程式為 x86-64，第三方函式庫位元數必須一致。L5：僅處理近似正對拍攝，大旋轉與梯形不在自動流程內。L6：YOLO 框只取一個，多色卡同框不支援，干擾類別一律忽略。L7：C 端不套用 EXIF orientation（沿用 WIC 管線現況），因此含 EXIF 旋轉資訊的直拍照片可能被判為直擺而失敗。L8：標準差類指標不具跨解析度可比性，因為縮圖統計本身帶有低通效應，偏小程度隨原圖解析度改變；同解析度下可比較，跨解析度僅供參考。

## 三、設計決策

D1：Stage A 沿用既有推論鏈（`yolo_post.c` 的 letterbox 與解碼＋常駐工作執行緒），不重寫，直接吃最高分 `color-chart` 框；該鏈已通過端到端驗證且輸出形狀與 Python 一致。D2：影像運算採 MSYS2 ucrt64 OpenCV 4.12 C API，MinGW 直接連結，免 shim 免 C++。D3：Lab 複用 `analyze.c`，以 D65 一致性比對；超標先修既有實作，不另寫第二份。D4：Y 沿用 `0.114B+0.587G+0.299R`，標準差逐像素浮點。D5：內縮比寫死 double 常數 `0.3`。D6：網格精煉以 Python 原版為準，不抄精簡版（缺缺口填補、跨軸借用、小間距保護）。D7：疊加圖層為影像、洋紅框、二十四格青色、ROI 框（最上）。

D5 說明：C 的 `10/3` 得三，語義全錯；float `0.3f` 轉 double 為 0.3000000119，使截斷得六而非 Python 的七。必須用 double `0.3`（測試已驗）。

## 四、Stage A：YOLO 取框

模型為 `models/color_chart.onnx`，由已訓練的 YOLOv8n 權重匯出。實測確證：輸入名稱為 `images`，形狀為一乘三乘六百四十乘六百四十；輸出名稱為 `output0`，形狀為一乘六乘八千四百；opset 為十八。此即標準 YOLOv8 detect head，每一候選列為中心座標、寬高，加上兩個類別分數；記憶體排列為通道優先，第 c 個通道第 i 個候選位於 `out[c*N+i]`。

取框規則：信心門檻零點二五，非極大值抑制的 IoU 門檻零點七，兩者皆沿用既有預設值。只保留類別一（`color-chart`），類別零（`122`）為干擾類直接捨棄；抑制後取最高分者一個，輸出原圖座標系的中心與寬高。若無框，整個定位流程不啟動，維持既有的偵測顯示。

需注意前處理與 Python 端的補邊位置描述有差異，但既有結構已把比例與補邊量記錄在轉換結構中，屬通用式可正確還原，因此不需改動既有解碼，也不影響定位正確性。

## 五、Stage B：裁切與縮放

以框中心為準放大一點二倍：縮放後寬為原寬乘一點二，高同理；左上角為中心減半寬半高後夾在影像範圍內，右下角為中心加半寬半高後同樣夾住。夾住的邊界分別為零與影像寬高。

裁切結果若為空即整張失敗，失敗原因記為 `crop_empty`，回退手動模式。長邊超過四百像素時等比縮放至四百（採面積插值），否則不縮放；面積插值在非整數縮放比時需處理邊緣像素的部分覆蓋權重，此為與 OpenCV 行為一致的關鍵細節。

必須記錄原點與兩軸縮放比。原點為裁切左上角座標；縮放比必須分成兩軸各自計算，因為縮放後尺寸經過整數化，兩軸的比例不會完全相等，而 ROI 寬高僅約二十餘像素，使用單一比例會產生可見誤差。

本階段除面積縮放外無影像運算依賴，因此面積縮放列為第一階段可先行的部分，不受影像運算庫選型的影響。面積縮放以手寫實作約六十行，含邊緣權重。

## 六、Stage C：網格線偵測

輸入為第二階段產生的四百像素以內縮圖。流程為邊緣偵測、線段抽取、方向分類、位置合併、軸向精煉。

邊緣與線段：先轉灰階，再以五乘五高斯模糊（標準差為零，即依核大小自動決定），接著以 Canny 邊緣偵測，低閾值五十、高閾值一百五十、孔徑三；最後以機率式 Hough 變換抽取線段，半徑為一、角度為一度、累加器門檻四十、最短線長三十、最大間隙十。參數全部沿用原版，不得調整，否則與 golden 期望值不符。

方向分類：計算線段角度，取絕對值小於十五度、或與一百八十度相差小於十五度者為水平線；與九十度相差小於十五度者為垂直線；其餘一律丟棄。此容忍度可涵蓋輕微透視造成的傾斜。

位置合併：水平線取兩端點縱座標的平均，垂直線取兩端點橫座標的平均。將位置排序後做簇聚類：與目前簇平均相差小於二十五像素者併入該簇，否則結算上一簇並輸出其平均值。合併閾值二十五像素是以四百像素縮圖為基準調出的值。

軸向精煉共七步，以原版函式為準。

第一步方向判定：比較兩種假設的偏差總和（水平五垂直七、水平七垂直五），後者較小則互換目標（色卡直擺）；相等時維持預設。互換即本版判整張失敗，原因記為 `portrait`，因直擺區分順時針與逆時針，編號一可能落在任一角，與標準序對應未定；本版編號固定為橫擺影像的列優先順序。

第二步典型間距：取相鄰位置差的中位數，小於等於五像素時改用影像維度除以目標線數。品質判定為首末跨度大於維度一半且線數大於二；線數小於二時相鄰差為空，典型間距取維度除以目標線數、品質為否，不走無效值路徑。原版即為維度除以目標線數，此為後備估計非間距公式，待 golden 複驗。

第三步跨軸借用：一軸品質良好、另一軸不良時，好軸間距借給壞軸；兩軸皆不良則不借。

第四步缺口填補：相鄰間距大於典型間距一點五倍時，均勻插入「缺口除以典型間距四捨五入減一」條。

第五步數量不足：比較首線與起始邊、末線與結束邊的距離，大者那側按平均間距外推；線數小於二時用典型間距。

第六步數量過多：以首末中點為中心，逐條丟棄離中心較遠的一端。

第七步目標與失敗判定：目標水平五條、垂直七條。不足記 `no_grid`、直擺記 `portrait`、空輸入記 `no_lines`，最終顯示於狀態列。

## 七、Stage D：二十四格與數據

本節所有座標皆為縮圖座標，統計一律在縮圖上計算，與 Python 端一致。

幾何計算：水平五條、垂直七條各自排序後，以四列六行雙迴圈逐格處理。每格以相鄰兩垂直線為左右邊界、相鄰兩水平線為上下邊界，四邊各內縮百分之三十（保留中心百分之四十）。內縮量為邊界差乘常數零點三，運算後以整數轉型截斷（非四捨五入，與 Python 的整數轉換一致）。編號為列優先，第 r 列第 c 行為 r 乘六加 c 加一。

切片語義：外推可能產生負值或超範圍的線位置，須以輔助函式模擬 Python 切片。規則為：起點或終點為負先加長度；仍為負夾為零；超過長度夾為長度；回傳終點減起點長度，不大於零表空。此函式決定該格是否有效，是與 Python 判定一致的關鍵，單元測試須涵蓋負值與越界。

有效性門檻：有效格數須達二十三以上，以固定二十四格陣列加有效旗標保存，編號照跳號、無效格標記為無效；疊加顯示與後續色差計算依編號索引，不另設第二陣列以免對不齊。

原圖映射僅供顯示：橫座標除以橫軸比例、縱座標除以縱軸比例，再各加原點；以既有的影像轉視窗轉換繪製，與偵測框作法相同。統計一律用縮圖值，不用映射後值。

每格數據：其一為 BGR 平均值。其二為 Y 通道，以零點一一四乘藍、零點五八七乘綠、零點二九九乘紅逐像素計算，取平均值與母體標準差。其三為 Lab，沿用既有分析模組：sRGB 除以二百五十五、反 gamma（不大於零點零四零四五者除以十二點九二，其餘加零點零五五除以一點零五五後取二點四次方）、乘 sRGB 轉 XYZ 的 D65 矩陣、乘一百、除白點（九十五點零四七、一百、一百零八點八八三）、立方根分段（分段點六除以二十九），得亮度與兩色度分量；取平均值，並計算彩度與亮度標準差作為雜訊指標。

三項前置確認須在資料凍結階段完成：既有分析模組必須逐像素轉 Lab 再平均（否則無法得亮度標準差，若不符須重寫）；標準差採母體（除以樣本數）；累加用倍精度（Python 單精度有配對求和，C 用倍精度才能進零點零五容差）。統計逐格進行，不整張轉 Lab。

## 八、手動備援

自動流程失敗時，使用者依序點選左上、右上、右下、左下四點。作法為以四點求解透視變換矩陣，來源為單位正方形的四角；接著在單位正方形空間中計算每格內縮後的四個角，經矩陣映射回原圖，取多邊形內的原圖像素做統計。此作法不經重取樣、不需雙線性插值，因此標準差不被插值平滑，與縮圖統計的決策一致。

手動模式的格編號由點選順序決定，與自動模式的橫擺影像順序對應方式待確認後定案。透視求解為八乘八線性方程，以高斯消去實作約八十行純 C。手動點選介面屬第三階段工作；若確認延後，則第三階段同步刪除該項。

## 九、模組切分與 OpenCV 整合

模組切分如下：裁切縮放模組回傳裁切結果與原點、兩軸縮放比；灰階模糊邊緣模組；機率式 Hough 線段模組（輸出上限四千零九十六條，避免雜訊圖造成記憶體暴增）；位置合併模組；單軸精煉模組；雙軸精煉模組（回傳是否互換）；取格模組；每格統計模組；編排模組（跑在工作執行緒內）；疊加繪製模組（放在畫布模組內）。純計算層零 Win32 依賴，可獨立單元測試。

OpenCV 整合實測結論：核心與影像處理兩個標頭皆存在，具備灰階轉換、高斯模糊、Canny、機率式 Hough 等函式的 C 介面，可由 MinGW 直接連結，不需自製 C 介面層，也不需引入 C++。部署僅需核心與影像處理兩個動態函式庫，共約十三百萬位元組，放於執行檔同目錄；完整依賴清單待第二階段建置完成後以工具查出。

三個必須注意的實作細節：第一，標頭搜尋路徑必須寫成連寫形式，因該版編譯器對斜線方向的參數解析會失敗。第二，機率式 Hough 函式在 C 介面下為十個參數，需補上最小與最大角度兩個參數。第三，影像讀寫標頭已被移除，無讀檔函式，但本專案解碼沿用 WIC，不受影響。

一致性判準：不追求與 OpenCV 線段逐條一致，因為機率式 Hough 以隨機數決定取點順序，邊緣圖差一個像素即改變線段集合。判準改放在網格層，即精煉後的五條與七條線在排序後逐線的最大絕對差不大於一像素，再加上二十四格的 Lab 與 Y 容差。

## 十、執行緒與使用者介面整合

定位流程跑在同一條常駐工作執行緒（可由既有偵測執行緒擴充，或另起；建議前者）。觸發點為偵測成功且框數大於等於一。介面端先裁切再送工作，僅帶四百像素以內副本，工作執行緒不觸碰主視窗影像緩衝。取消沿用序號機制，換圖即丟棄；結果綁定影像序號存於全域狀態，換圖清除。

顯示：畫布新增疊加繪製，青色一像素線加一像素黑色外框，編號文字加背景，避免疊在色卡青色格或淺色格上不可見。狀態列複用訊息區顯示成功格數與耗時或失敗原因。檢視選單新增顯示開關，命令編號避開既有範圍。

設定僅在定位區段放啟用與顯示開關；信心與抑制門檻一律讀偵測區段既有值，不存第二份；內縮比與最少格數寫死。

## 十一、移植驗證

驗證三段：一、C 端測試程式以傾印模式輸出二十四位元、無壓縮、列對齊點陣圖，解碼用 WIC（不用 Python 讀檔）。二、Python 輔助腳本匯入原版函式，以無介面方式在各階段插入傾印，產出 golden JSON，不改原版邏輯。三、C 端測試程式讀 JSON 比對。兩端同一份點陣圖，杜絕解碼分叉；旋轉負例由點陣圖旋轉產生。JSON 標頭記錄 Python／OpenCV／numpy 版本與解碼器、EXIF（僅記錄不套用）；OpenCV 版本必須記錄，因不同版本線段抽取結果可能不同。唯一 golden 為此 JSON，既有網格圖與報表 CSV 降為人工目視參考，不用於自動比對。

JSON 逐階段凍結：解碼寬高與方向旗標、縮圖雜湊；框中心寬高與信心；裁切原點、裁切尺寸、縮放尺寸、兩軸比例、縮圖雜湊；原始線段、合併位置、是否互換、精煉位置；二十四格座標與有效旗標、每格統計。原版若跳過第一階段，該欄位記空，C 端走同路徑。

注入式比對：裁切縮放以原點陣圖加框為輸入，比對原點與尺寸完全一致、雜湊一致；合併以原始線段輸入，精確一致；精煉以合併結果加尺寸輸入，精確一致（涵蓋缺口、借用、互換、邊界）；取格以精煉結果輸入，二十四格座標完全相同；統計以 Python 縮圖加格座標輸入，平均值與標準差容差皆零點零五；邊緣加線段端到端比對排序後逐線最大絕對差不大於一像素；冒煙測試只驗取格成功與容差放寬。

容差表：注入式下網格線精確、Lab 與 Y 平均值不大於零點零五、標準差與彩度不大於零點零五；端到端下網格線不大於二像素、Lab 平均值上下零點五、Y 平均值上下一點零、標準差上下零點五且失敗僅警告。依據：內縮後中心約九像素，平移二像素仍落同格，色塊均勻時平均值變化小。

測試集為五正例加五負例。正例取既有樣本目錄五張。負例為無色卡（零框不啟動）、直擺（正例旋轉九十度，預期限直擺）、強模糊或低對比（明確失敗不當機）、貼邊使放大後越界（驗夾住與切片語義）、極小（裁切小於一百像素，不放大）。C 端執行體為獨立測試程式，只連結純計算模組與既有分析模組、WIC 解碼，不連介面層；暨印模式產點陣圖，預設模式讀 JSON 比對；另以除錯輸出印二十四筆統計作為最小資料出口。

## 十二、實作階段

第一階段資料凍結：以傾印模式產生點陣圖，執行 Python 輔助腳本產出 golden JSON，確認原版是否跳過第一階段，並完成既有分析模組的 Lab 一致性驗證。完成條件為 JSON 產出且一致性通過。

第二階段純計算核心：裁切縮放（含面積縮放）與合併、精煉、取格、統計五個模組，加上單元測試，涵蓋切片負值與越界、缺口填補、跨軸借用、橫擺互換、內縮幾何。除面積縮放外的部分與影像運算庫選型無關，可先行開發；統計模組需第一階段前置完成。

第三階段影像運算層：以 OpenCV 實作邊緣與線段抽取。完成條件為網格層不大於一像素，且端到端容差符合。

第四階段整合：工作執行緒、疊加繪製、選單與狀態列、設定，另加除錯資料出口。完成條件為全部測試通過。

第五階段驗收：全表通過、第三與第四階段在四百像素縮圖上合計小於五十毫秒、正例與負例行為皆符合預期。第二階段可先行，因為其餘部分皆無影像運算依賴；第三階段則需等選型確認後始動。

## 十三、待確認事項

第一項已定案：影像運算採 MSYS2 OpenCV 4.12 C 介面並動態連結；原草案的三個方案作廢。第二項：手動備援介面延後，本版只做自動流程與狀態列提示。第三項：patch 數據不進匯出，僅保留記憶體結構與除錯出口。第四項：疊加樣式為青色線加黑色外框。第五項：內縮比與最少格數寫死，設定僅放啟用與顯示開關。第六項：第二階段發包條件為原版查證回填完成且第一階段產出第一份 JSON。第七項：直擺色卡判定失敗。第八項：統計在縮圖上計算已定案。第九項：以 WIC 解碼為準、不套用 EXIF 已定案。第十項：測試集為五正例加五負例。

## 十四、主要風險

第一，直擺與梯形不支援，本版判定失敗並回報原因。第二，OpenCV 版本差異會改變線段集合，對策是判準放網格層並記錄版本。第三，縮圖統計的標準差跨解析度不可比，列入已知限制。第四，工作執行緒與介面的影像所有權需明確：介面端先裁切、所有權轉移、結果交回介面端釋放。第五，超大雜訊圖可能造成線段暴增，以四千零九十六條為上限。第六，內縮比浮點精度已由倍精度常數與測試保護。第七，既有分析模組若為先平均再轉 Lab 則需重寫，屬第一階段前置風險。第八，失敗原因完整性依賴原版查證，需在測試集補齊案例。
